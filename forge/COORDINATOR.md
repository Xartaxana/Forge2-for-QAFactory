# forge/COORDINATOR.md -- rules of the Lead and the Architect (forge 2)

Read at every session start by the Lead and the Architect. Worker rules are in `CLAUDE.md`; a rule stands in one file only. Legend of `rows:` lines and tool markers: see `CLAUDE.md`. The commit that lands a card removes that card's `not built` marks in the rule files (case: plan S3, six marks left stale).

## Acceptance
- Acceptance comes only from a tier above or with critic input; no session certifies its own work, and a worker never writes accept or reject. A builder accept with no critic input under its task was self-certification. (case: FH-6111, a worker certified its own work; FH-3055)
- A negative claim in a report or a digest is always spot-checked by the acceptor with a same-form control before it is used. (case: FH-1042, FH-5016)
- Acceptance -- the witness run (B18) and the owns check, `git diff --name-only main...w/<task>` against the dispatch's owns -- comes BEFORE the fast-forward: once the branch is in main that diff is empty; a path beyond them stands in the hand-back as needed beyond the manifest, or the work is returned. (case: FH-4045, FH-4046)
- A hand-back missing its `similar:` or `friction:` line is returned before review. (case: P12, B6)
- A cut worker's hand-back is taken as done and not done; the rest goes whole to a fresh worker, and its partial output is never accepted as done. (case: W-46, W-81; B5)
- A test that fails only under load is a defect of the test, fixed, never retried. (case: FH-2093, the old forge kept a queue of known-flaky tests)
- A scout digest is accepted by its trail: the acceptor checks that the question is covered and spot-verifies one load-bearing claim; a digest with no trail is rejected. (case: dev1.jsonl:252 and :274, a false negative and a stale status found by the Lead's spot check)
- A builder hand-back is accepted by its witness, the command and its actual output; a report without one is rejected, and a retelling is no witness. (case: dev1.jsonl:3655, a build report with no witness)
- A diff over about 100 lines, one touching a schema, money or a core, and a plan that forks get an independent critic review before acceptance; the builder's own run is the first filter, not a substitute; a skip is a written note with its reason, allowed only to an acceptor above the executor's tier. (case: dev1.jsonl:5810, a critic blocker on a builder diff)
- A fix to a role's behaviour is proved only by a live run of that role; what a person pastes in for the role proves nothing, and until the run the item is coded but not verified. (case: dev1.jsonl:635, critic t-240 found a role-text change closed by code with no live-proof row, fix P11-1)
- The Lead's own acceptance is judged from outside: the weekly calibration reads the journal for acceptances with no witness or critic input, and the Architect reviews mechanism commits. (case: dev1.jsonl:339, an acceptance that missed the card witness and the lint run)
- A task with a UI result: the verification run includes DRIVING the UI, and the witness is a before/after screenshot or recording; a purely textual witness is insufficient. (case: old rule 1019)
- Accepting workers happens in a BATCH at a stage boundary (accepting everything stays mandatory), and one question to a person carries a list instead of a round of clarifications. (case: old rule 1093)
- A fix round runs in a FRESH worker carrying only the diff and the verdict; a re-review carries only the fix diff and the verdict. After a critic verdict `fit_with_fixes` on CODE the Lead checks the fix round itself only inside the border: the fix diff does exactly what the verdict's `fixes` prescribe and adds no new logic (no new function, branch, state or write path). The base is the reviewed head: the Lead COMMITS the reviewed state before each critic dispatch and writes the bare token `reviewed:<sha>` (from `git rev-parse HEAD`) as the first token after the model label in the critic call's `description`; with no such commit the fix round is `nobase`. A counter measures the fix diff against that base: border 0 means no counted kind of change. Inside the border the Lead walks the fix diff by the critic's standing questions Q1-Q12, one line per question plus one per fix (`fixed: <where>`, or `not fixed` -> another fix round), and the accepted notes carry `fixes checked by Lead: <verdict path>, border 0`. Outside the border (any count above zero, no `reviewed:` token or a cut one, a base that is not an ancestor of HEAD, a `blocker` verdict, a fix that cannot be matched to its verdict line, or an acceptor not strictly above the builder's tier) the critic re-review carries only the fix diff and the verdict, and its dispatch names the case `re-review: logic or nobase or blocker or unmatched or tier`. (tool: none yet) (case: old rules 1096, 1101, 1102)

## Escalation and delegation
- Two failed attempts on one tier, or an explicit "this is beyond my level" signal from a worker, move the work one tier up, journaled as an `escalated` event whose note starts with `<agent>: ` (the role the work moves to); the task stays open and the higher tier's dispatch continues it; no silent retry on the same tier. Builder rejects are counted per task by `journal.py rejects <task>` (tool: B18, not built). A critic verdict with fixes that the Lead accepts counts as a rejection, and its fix round is attempt n+1 of the same task. (case: FH-1038, the old forge's tier rule after two rejects; old rule 1047, returned by the owner 26.11.2026)
- A task that turns out to be decomposable is returned to the Lead by the worker's `decomposable: <split>` hand-back and journaled as a `decomposable` event, the split in the note. (case: old rule 1045, returned by the owner 26.11.2026)
- A second reject at the Lead's tier whose verdict names no blocker and whose fixes add no product logic (test rows, wording) does not wait for the Architect: the Lead dispatches one last round with those fixes only, checks it itself, and writes the work-list record `--for architect` as a note naming the verdict. A finding that appears after that round goes to the work list, not to another round. A blocker, or a fix that adds logic, goes up as before. (case: C1-5 t-1986 and C1-2 t-1995, 26.11.2026)
- Questions go up, work goes on. To the Architect, as a work-list record `--for architect` (B11): a second reject at the Lead's tier (fr:A13), a conflict between two rules or between a card and a plan decision, a process trade-off, the shape of a new idea. The record names what waits and what does not. The Lead never stops for it: it takes the next work the question does not block; only the named card waits. An Architect session answers every open record with a decision or `left: <why>`; the answer is committed and the record closed with that commit. The Architect is never a subagent: the owner switches the session. (case: W-83; the old forge's architect queue)
- After two rejects with `failure_class: spec` in the reject note on one task the spec was wrong, not the work: the card goes back to the designer for a re-spec, not to another fix round. A card has a TOTAL ceiling of four fix rounds across all reject classes (the last-round exception above included); after the fourth the card goes to the Architect or the owner. (case: owner's question 26.11.2026, why a fifth round when the ceiling is 2, W-189)
- When escalating to the Architect the Lead tells the owner, in Russian, that calling the Architect is better, with the question in one line. (case: old rule 1054)
- A new owner decision opens a new node of the graph and is not poured into a running task. (case: old rule 2025)

## Delegation and roles
- Large specs -- a writing dispatch with 3 or more numbered items, or touching 3 or more files -- are drafted by a designer in an independent context (counted by code, tool: none yet; the Lead drafting it anyway is legal ONLY with a `dispatch_skipped` event whose note starts with `designer: ` and then names the reason, the motive being an independent drafting context and not model price; below the threshold, and for intent briefs, the Lead drafts freely with no event; the threshold counts the task's primary draft, a resubmission under the SAME task_id continues the spec and the Lead edits it itself with no event, work re-badged under a NEW task_id is a new task; a narrow node is written by the Lead in the dispatch with a `dispatch_skipped` note when the designer would cost more); the designer returns forks, never decides them; brief facts are measured by code first. (case: owner 17.11.2026, fr:A9)
- A designer's draft is accepted against the dispatch form, edges with invariants, readers of every touched file, forks returned as questions, and at most 40,000 bytes. (case: W-97, W-96, fr:B4)
- The Architect takes the owner's new ideas, process escalations and the weekly calibration (`forge/calibration.md`). (case: D-0067 of the old forge, fr:B6)
- A new idea: ask the owner about intent first, then a goal document by `.claude/skills/idea-goal/SKILL.md` (eight steps) with measured success, carried facts and reasoned exclusions, before any design. A large idea keeps its goal document and one work-list record of kind `idea` pointing to it. (case: owner 11.11.2026, fr:A25)
- A step that code takes over from a role is compared with the role's own reference run before it is trusted; any result below the role's stops the move. (case: the old forge's S0 ticket snapshot lost the acceptance criteria, comments and parent unnoticed, docs/PROJECT_FULL.md of the old forge, section Package change, item 5)
- A spec that changes the meaning of a field, condition or gate has its data premise measured on real data (one command, the result in the spec), its error direction and awkward inputs written before code, and its text read by a critic as a plan; cost: one critic run on the plan per such spec or spec edit; detector: two `reject` journal lines on one task_id with `failure_class: spec` in the reject note mean this rule was missed (discipline, no code gate). (case: dev1.jsonl:5424, a premise measured bare and false; docs/FINDINGS.md F-2 of the old forge; old rule 2026)
- A claim that a delivery form or a policy pays is measured against a free-agent arm on the same tasks, with the price per accepted task. (case: docs/tasks/specs/reviews/t-354-tests-factory-vs-free.md)
- Closing a defect walks the axes of `forge/siblings.md` that it sits on; the table starts empty and an axis enters it with a caught case. (case: dev1.jsonl:1825, a SIBLING_MAP row left untouched)
- Recon goes to a scout by default when the answer needs more than 1-2 known files or any repo search; the Lead reads itself only a single precisely known target; up to about 4 known targets are legal ONLY with a `dispatch_skipped` event (reason mandatory), never silently; recon of unknown scope is always a scout. (case: old rule 1011)
- A journal `dispatch` line that sends an idea to the designer with no preceding Lead plan shown to the owner, or with no critic on the plan, is a miss (detector: discipline, no gate). (case: old rule 2038)
- The visible dispatch label (`description`) starts with the worker's role and a colon ("builder: ..."). (case: old rule 1059, D-0016)
- Background execution by default (`run_in_background`); synchronous only when the next step depends on the result AND no other work or operator question is pending; accepting the result on completion is mandatory. (case: old rules 1057, 1058)
- SMALL-WORK BATCHING: a small builder-class edit that does not block the next step accumulates in a session list and goes to a builder as ONE batched dispatch at a stage boundary (marker `small-work batch`); self-execution with a skip event stays legitimate only for an edit that blocks the current step, and the reason names the blocker. A reason of the class "the operator is waiting / an interactive request blocks the move" justifies self-execution only on the FIRST such move in a session; from the second, a non-blocking edit joins the batch and a blocking one goes out as an immediate solo builder dispatch, never self-execution and never a batch entry (self-execution there is a violation). (case: old rules 1063, 1065)
- Launching or collecting a deterministic script (exam runner, validator, health check) is an environment operation: no skip event, but its result lives in its own carrier, and a run with no carrier trace is a violation; in doubt (the run embeds judgment) the skip event is the safe default. (case: old rule 1066)
- Fix the class: FIRST apply the class to every neighbour inside the SAME artifact (sibling subsections, clauses of a rule, entries of a list, branches of a parser), before the sibling-axis walk, which the sweep never replaces (a class living in both gets both). The sweep unit is the enclosing structural block, widening to the whole file only when the move already read it; opening a file specially for the sweep is forbidden (move it to another node instead). The sweep is an ENUMERATION with a verdict per neighbour (applied / not applicable and why / moved, with its id); prose "neighbours checked" is not execution; none found gets the line `no neighbors: <why>`. A sweep unit over roughly 150 lines, or with more than 5 neighbours, goes to one scout dispatch carrying the applicability question, or carries a `dispatch_skipped` event. (case: old rules 1073, 1074, 1075)

## Parallel writers
- Parallel writers own disjoint paths; a shared file has one writer; nobody commits another session's uncommitted paths. The goal is six writing builders when there is parallel work, and no fewer; designers, critics and scouts are not counted and never wait for a slot; a seventh when the coordinator needs it, for example a red CI to fix, through the dispatch note `seventh: <why>`; six is the goal, never at the cost of efficiency; an owner's narrower limit holds for one session. Six gaps, one rule each (tools: B14, B17, not built): (1) task ids are issued by `journal.py --event dispatch` without `--task`, never invented; (2) a work-list record is taken `in_work` by one session, another takes over only with `--take-over --reason`; (3) a builder writes only in its own linked worktree on branch `w/<task id>`, the Lead pushes main before `git worktree add`, Lead and Architect edit in the main checkout and commit only their own paths, `git commit -m <msg> -- <paths>`; (4) tool-written stores (`forge/worklist.yaml`, `forge/owner-words.yaml`, journals) are written only through their tools, hand-written files only when `git status --short <file>` is clean; (5) the refusals and the neighbours are printed at start (B2); (6) a dead session's work is closed by the Lead: its open dispatches by `journal.py --event return`, its takes by `--take-over`, its uncommitted paths only when no live neighbour exists and after reading the diff. (case: W-84; plan 26.11.2026 about 02:24 item 3, her words of 16.11.2026 await their record; plan record 25.11.2026 23:50 point 4; FH-6064, workers lacked unpushed commits)
- A cross-deployment queue item exists only if written, in the same move, into a carrier the TARGET reads at boot; a session's own journal notes or findings log are not such a carrier. (case: old rule 1039)
- In the same move as a merge, the statuses of the nodes are updated and merged branches and worktree folders are removed. (case: old rule 2071)
- A session that writes in the main checkout not on the Lead's behalf (a second Architect session, say) sends its commit straight to origin/main by its own road, or puts its records through a `w/<...>` branch; after a push from a branch the Lead fast-forwards the main checkout's local `main`, and the session start print shows the main checkout's ahead/behind. (tool: ahead/behind print, none yet) (case: plan S10, B14: six local commits against six pushed in 26 minutes, both appending the tail of one plan file)

## Journal, sessions and retro
- What code can do, code does: journal lines, dispatch headers, merges. The journal is append-only, written by `journal.py`; a fix is a new line. (case: W-99, fr:A15)
- Knowledge lives in repo files, not in a machine's memory: what a session learns about the work (an owner's word, a rule, a lesson) goes into a file the next session reads; personal memory holds only machine paths, tokens and local processes. (case: owner 30.10.2026, docs/PROJECT_FULL.md of the old forge, section Teamwork, item 10; B-forge-8)
- A batch closes by finishing the work, not by carrying it over; a carry-over is confirmed by a person. (case: W-98, fr:A26)
- The next session recovers from files alone; a retro is written while the reasons are in context. (case: owner 17.11.2026, 24.11.2026, fr:A28, fp:A26)
- On a trigger -- the person's words about a compaction, a pause or the end of the day, a manual compaction, a phase close -- the Lead answers "what of today's work will the next session not see in files?", writes each item into its carrier (owner's words and decisions to `forge/owner-words.yaml`, plan changes to plan or spec files, task state to the journal, the state line to `forge/BOOT.md`, measured numbers to `measure/runs/**` with their command), then runs `journal.py --event session_end --note "unseen: nothing"`. (tool: `forge/carriers.json`) (case: plan record 25.11.2026 19:20, a conclusion that stayed in a session and was lost)
- Before `session_end` the Lead runs `retro.py write`, writes a reason per non-zero counter and answers its questions, names the file in the note, and says one short list in plain words: at most five important points and every open owner question. (tool: `forge/tools/retro.py`) (case: W-82, B9)

- Outside input (a CLI, a ticket, a person's words, a config, a host answer) gets an adversarial mini-battery -- magnitude, nesting, encoding, empty or broken input -- and every limit applied to it a case AT and BEYOND it, each a table row. (case: W-85, W-86, fr:A3)
- A spec names its edges: every limit, every empty or absent input, every pair of its own requirements that can conflict, every artifact the change brings into existence (both worlds), each with the invariant it protects. A silent edge is the dispatcher's defect, never the performer's guess. (case: dev1.jsonl:1120, a DoD line silent on an edge; t-896, 65 spec rejects of 11-16.11.2026)
- A node is written for a weaker model: file, function or field, expected behavior and a test per item; the direction is chosen, not listed as options; a fork the writer cannot decide is a question with a recommendation, and the node runs on it. (case: W-91, docs/PROJECT_FULL.md of the old forge, section Teamwork, item 11; B-forge-8)
- Before sending, the dispatcher runs the five-point checklist: (1) an explicit question or completeness criterion, or acceptance keys; (2) the DoD inline AND the edge behaviors named -- limits/truncations, empty/absent inputs, conflicting requirement pairs: stated, or explicitly forked up; (3) `given` enumerated and sufficient -- data, fixtures, paths named, not implied (its sufficiency is the Lead's responsibility); (4) a writing dispatch: owns, non-goals, handoff present and its witness scope named; (5) freshness: the spec's load-bearing facts are checked against their carrier, not memory. A checklist miss exposed by a reject or a finding is a spec defect of the dispatcher (a calibration case); promotion to a machine layer follows the next recurrence. (case: old rules 32, 33, 240, 244)
- A scout dispatch carries an explicit question and a completeness criterion ("X is nowhere to be found" is a valid outcome and requires a trail); a critic dispatch attaches the spec/DoD of the work under review, otherwise only general quality is checkable; for a targeted read-only dispatch the manifest is the explicit enumeration of what is attached. (case: old rules 21, 23, 29)
- A DoD is inline, and the edges and the non-goals stay inline too: a bare pointer to a spec file or an earlier event is not a DoD. A brief carries FACTS by pointer: `given:` names the frozen file and the digest's objects by their exact ids (`q2a, q2b`), never by a prefix; changing code is pointed at by `path::symbol`, not a line range. (case: old rules 35, 245, 246)
- A writing dispatch's `given` manifest is a MARKED declaration: an inline enumeration, or a pointer to a persisted spec that itself carries the enumeration, one hop away; no marker, no manifest. `owns` is always given inline, never by pointer. A gate refuses a dispatch without the header lines and names what is missing; the informed pass is a line `manifest-skip: <item>[, <item>] -- <reason>` (manifest-skip: tool: none yet). (case: old rules 41, 45)
- Over the designer threshold a dispatch carries `designer:` (the accepted draft's absolute path, `skip -- <reason>`, or `resubmission <task_id>`); a designer dispatch also carries `facts:`; a critic or designer dispatch carries its report path on `handoff:`, never `owns:`, one `.md` file in the role's folder, and a gate refuses otherwise. (tool: none yet) (case: old rules 46, 48, 50)
- A spec says which move creates an artifact the change brings into existence, and when it prescribes WHERE in existing logic a branch goes it states the invariant that position must preserve (what stays unreachable, what must still be refused). (case: old rules 236, 237)
- A parallel fan-out declares ownership per path (see Parallel writers) plus an optional `maxConcurrent` cap. (case: old rule 241)
- A worker returning a DoD-less or manifest-less dispatch is an emergency net, not the normal cycle: frequent returns are a coordinator defect flagged at calibration. (case: old rule 40)
