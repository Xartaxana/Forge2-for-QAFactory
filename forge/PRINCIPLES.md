## Principles
- P1: Code helps a role and never hinders or replaces it: the role itself calls the script and itself decides what is missing and how to fix it; on the unforeseen, code reports and does not stop the factory.
- P2: The factory is universal: what varies across projects is never turned into code.
- P3: The conductor is a helper for problems, not a launcher of commands; commands are launched by code on a stage transition or when a question appears.
- P4: Gathered material is passed on in YAML, so that nothing is lost.
- P5: Data, above all the task's source data, is obtained by every route: API, SSH, browser; with no access, ask the person with the options "not needed / here is how to get it / here is the text". An LLM agent is not a read source: the ticket, its links, comments and attachments are read by API, repositories by API or git; an agent is used only for writes, and only where the project writes that way. "Ask" covers only access the person CAN give; what the factory's own probe proves unreachable (no VPN, no tool, a file too large) is a gap by default and a report line by name, with no question; one recorded decision on a class holds for all its instances until the end of the run. The factory neither promises nor attempts what is impossible in advance.
- P6: The judge (the factory's cheap external judge service, config `judge.provider`) is not there to save on the judge itself but to take expensive actions off the LLM.
- P7: The factory runs on Sonnet or Terra; Haiku is used nowhere.
- P8: Experiments comparing factory versions leave no traces in the project: no MR, no tracker comments or subtasks; bugs go only to a Markdown file or the chat.
- P9: Every question to a person is in human language, with no internal names (never `person.review_recorded`).
- P10: Keep a map of the project and its axes of symmetry: similar logic at different stages gets one approach.
- P11: The friction of roles against our code is measured; code that makes a stage dearer is a defect.
- P12: Every piece of new code is checked for similar places and for friction.
- P13: A person's word carries the factory through any gate; the pass is recorded in the findings.
- P14: Roles get only the tools they need.
- P15: A refusal says what is wrong and what is expected; it never names a path or tool unavailable to the refused party and never locks the role in; a ban is never bypassed, but it always has a door; a role caught in a trap files a finding.
- P16: Pyramid: as few e2e cases as possible -- a change is checked one level lower wherever possible; cases are merged (parameterisation, several checks in one scenario); "one behaviour per case" is a unit-level rule, not an API or e2e one. The one condition for merging: the red line shows which case and which branch failed (the parameter id names the case); inputs the application all treats the same way are ONE parameterised test, not several cases.
- P17: A case says WHAT to check; the automator decides HOW. Cases and autotests relate many-to-many. The automator picks the pyramid level, extends existing tests, parameterises and merges checks; the goal is everything checked at the least cost and nothing missed. Code at the S5 exit checks completeness only -- every Then of every case is bound to a test or to a recorded reason -- and never requires the code to match the plan's hint (`fit`). The code critic judges the automator's choice: was a level higher than needed taken, does a test repeat an existing one, was a new test written where an old one could be extended.
- P18: The price of a task is one and true: it includes everything spent on the task (roles, the conductor, answers to the person in chat, agent calls) and must equal the sum of the spend per agent. Equality of two independent sources is the check of our accounting; a discrepancy is a defect that is fixed. While the sources disagree, the price is printed as a range "from ... to ..." with a mark and a finding naming where; one wrong figure is never shown as exact. Money is never written into repository files (the report). Steering (choosing a role and returning work to it) is the conductor's spend; rework is the role's spend; gathering data is the scout's spend.
- P19: How to check a case is decided bottom-up through the pyramid, always in this order: (1) an API-level or component autotest, if possible; (2) if not, e2e: extend an existing suitable e2e check or write a new e2e case; (3) if it cannot or need not be automated (the case is not in the regression), the agent checks it by hand and shows the person "before / after"; (4) if the judgement is subjective, or only a person can make it faster and cheaper, a person checks it by hand; (5) if the test can be automated but in principle cannot run on this environment, the test is written and a person runs it on another environment. A case that becomes automatable after the person's answer walks this ladder again.
- P20: Code is never the oracle: a test whose expectation is taken from the implementation can only pass. The expected value comes from the requirements (description, AC, comments, attachments, linked tasks, spec, a precedent a person confirmed); when the requirements are silent, the question goes to the person, who is shown how it was BEFORE and how it is NOW, and until the answer the expectation stays open (`unresolved`), never a literal. A requirement derived only from the implementation diff is a statement about behaviour that the person confirms or rejects. A "before / now" difference is always highlighted to the person; with no answer it is a GAP in the report, neither green nor red.
- P21: Delivery has three outcomes, not two: `delivery_ready: yes` -- everything checked; `no` -- a bug or a gap found (the product cannot do what a register requirement demands); the third -- "ready once the person finishes the checks": the factory found no bugs or gaps, but some cases went to the person or another environment (P19, rungs 3-5). Then the report section "Left with you" names each such item with its command or steps, and the regression testing with its scope in the factory's opinion. A missing item blocks the REPORT (code matches the section against the ledger and refuses), not the verdict; a regression not recorded in the S3 plan is an explicit gap line, never an invention. What is handed to the person does not hold delivery -- only what is left unsaid does; the third verdict opens outward everything `yes` opens.
- P22: When the factory cannot cope, does not understand or cannot act, it calls the conductor, and the conductor sorts it out; this is a principle of the whole factory, not the answer to one gate. When code meets a state it has no move for, it calls the conductor, and the conductor offers the person everything that lets work continue, with the price and the consequences for the person and for the story of each option; it executes the chosen one with existing commands and records a finding. The conductor itself redoes nothing: it steers the factory -- calls an agent (through the controller), returns the factory to the needed stage, asks the person to do something. Code puts only closed questions to a person (the factory's question form) and reads only those; any free answer is read by the conductor, never by code. The run must not suffer: the worst allowed is the conductor spending unplanned money; not allowed is the factory standing still, or promising and not doing. Investigate first, always and everywhere: a cause, verdict or refusal recorded by code is evidence for the investigation, never the ready text of a question; before any question to a person the conductor reads what the code left (records, logs, notes) and asks only what only the person can know or decide. This rule is one for the whole factory, not a line in each phase.
- P23: The factory works by REQUIREMENTS, not by AC. Acceptance criteria are one source of requirements alongside the description, comments, attachments, linked tasks and the diff (statements from the diff per P20); a task may have no AC at all, and its requirements are still derived and checked. Everything that counts completeness (the S2 register, the S3 plan, the S4 cases, the Then binding in S5, the delivery verdict) counts by the register's requirements; the wording "every AC" in a rule, form or brief is a defect of its carrier.
- P24: The factory FINDS regression and hands it to the person, but never runs it itself. The list is not cut to what our stand can do -- the person may run it on another -- and each item names its stand requirements. A story has ONE run, so the list must be right the first time: only existing tests (none written in this same run), real paths, one command runnable on another machine, with no repeats. "Instability between runs" is not a regression defect.
- P25: Host and gateway settings through which a project reaches the models (for example the prompt cache TTL) are the project's given, never a thing to edit. Never propose a gateway or host setting as a cure for the conductor's cache rebuilds; savings live in the factory's own code and flow. A keep-alive poll is not built either.
- P26: A manual case is walked by an agent; the evidence behind it is written by code. The agent goes step by step live, watches what happens and adapts; each step is executed by a factory tool that itself records the evidence (snapshot, page text, requests and responses), and the agent's conclusion is accepted only if it quotes recorded evidence. The agent records ALL doubtful places as it goes, not only the case's outcome; each such observation goes to the analyst for a "bug or not" judgement on a par with the Then result. The analyst walks every suspicious unconfirmed place and finds the truth: no place stays "not confirmed" -- the analyst walks it by hand through the walker with the recorder's evidence and answers one of three: bug, not a bug, or the requirement is silent -- a question to the product owner (P20). Next to each verdict the SOURCE of the expectation is named (a register requirement or "derived by the factory"). The places (red tests, the recorder's `surprise:` lines, runner observations, "not confirmed" bug drafts, discrepancies in the requirements register) are gathered by code and judged by a role (P27). For the S6 exploratory charter the Playwright MCP browser is allowed, but every step goes through the factory's recorder -- evidence on disk, and quoted; input in steps is typed character by character, as a person would; after a step the recorder flags oddities as `surprise:` lines.
- P27: Code owns data, the role owns judgement and outcome, the person owns intent. Code reads the ticket, diff, attachments and stand, assembles YAML, carries the person's words, checks keys and cross-references -- and does NOT decide whether an obligation is closed, whether a case is fit, whether a red is a bug; the role decides that, and a tier above accepts its outcome on meaning with a witness; the person decides at gates what only the person knows. A role's rule is a tester's experience (where to look for bugs, techniques, how to write a stable e2e), not a form procedure. A loss in a handover is cured by code only when DATA was lost; lost judgement is cured by a charter, acceptance and a question upward. The radius of a change ("what else could break") is the role's judgement, not code's: a blast-radius tool and the like give evidence the strategist reads as hints; the radius in the plan is the strategist's conclusion with a reason, and code never calls its index a radius nor judges regression completeness by it.
- P28: What is automated is what will run many times and what is red. The strategist (S3) decides for each plan row: (1) the check goes into the project's regression -- an autotest; (2) it is red (the expectation differs from the behaviour) -- a failing autotest attached to the bug; (3) a one-off check of a new feature that will not go into regression -- the agent by hand (P26). P19 answers only the question of the LEVEL of what was decided to be automated; the automator (S5) still decides HOW (P17).
- P29: An autotest is written by first deciding which checks are independent and which are sequential. Independent checks never stop each other: one failure does not hide the rest. Checks are sequential only when they depend on each other. A red probe for every check: independent ones are seen in one run, dependent ones in one run per link.
- P30: The red probe by default substitutes the value a broken product would give, and the test must fail; the role proposes that value. Only if the role knows no other value is the check inverted -- in any language. Without a role, only our own error text in the failure proves it; in every other case the role looks.
- P31: Different working paths for the same thing are a bug: everything is uniform, with no exceptions for languages, projects or cases. An exception is possible only by the owner's word.
