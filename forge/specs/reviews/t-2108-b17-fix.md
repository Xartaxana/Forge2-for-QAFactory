N1 (fix before merge; not blocking on its own: SessionStart runs only in the main checkout, plan S6) session_start.py::git_hooks_text and test_hooks.py::test_session_start_f3_f4_f6 (last assert). The fix round resolves a relative `core.hooksPath` against the MAIN checkout (`os.path.join(main, val)`) and the docstring says this is "resolved as git does: against the top of the work tree". Git resolves it against the top of the work tree the hook runs in. Measured in a scratch repo (hooksPath `forge/hooks/git`, the hook file only in main): a commit in main prints `MAIN-HOOK-RAN`, a commit in the linked worktree runs nothing (rc 0, no line); git_hooks_text from that linked worktree -> `hooksPath ok, 0 of 1 tracked executable (1 untracked)`. Card B17 (c) (FH-2030): "wired when core.hooksPath resolves to forge/hooks/git of this repository, from a linked worktree to the main checkout's". So from a linked worktree a relative value is `wrong`, and the new row pins `hooksPath ok` there: a false known value, and a docstring that claims the opposite of the code. Fix: resolve `val` against `git rev-parse --show-toplevel` of `root` (one more call in the shared budget) and compare to `<main>/forge/hooks/git`, keep the file count and ls-files in main; the row expects `hooksPath wrong: forge/hooks/git, 0 of 1 tracked executable (1 untracked)` from the linked worktree and `ok` from main. (The other way out -- keep main resolution and drop the claim -- would leave the line contradicting the card's linked-worktree rule.)
