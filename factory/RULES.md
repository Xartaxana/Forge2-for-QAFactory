# RULES.md -- rules for building the factory

Rules of the factory's craft, for whoever changes the factory (not for the factory's own roles). Restored from the old forge at sha b01363a15: the rules behind `docs/FACTORY_RULES_INDEX.md` (full text `ai-packages/qa-factory/design/factory-rules.md`, ids FR-n) and `docs/ARCHITECTURE_INDEX.md` (full text `ai-packages/qa-factory/design/architecture.md`, ids AR-n), grouped by the old headings; reasons and examples dropped. An AR invariant that restated an FR rule is merged into that rule's line, and its id stands on that heading's `carry:` line. `P<n>` is a line of `forge/PRINCIPLES.md`. Old package tools do not exist here: a duty a tool would enforce ends `(tool: none yet)`. Each `carry:` line names the carry-ledger ids restored under its heading.

## Refusals and doors
- The door a refusal names is one the refused party can use: a role's refusal names a command in that role's own permitted set, the orchestrator's names an orchestrator operation; a refusal never names a path or tool the refused party cannot reach and never leaves it without a move; a test opens every door a refusal names (P15).
- A reason owned by the factory is reported to a person, in a section that says it is the factory's, and never put to them as a choice: nothing is asked of a person for the factory's own defects; every reason reaching a person carries an owner, and only `product`, `person` and `environment` reasons are phrased as decisions.
- A stage may not require, to close, an artifact nothing in the factory can produce: for each completion requirement some command builds it, and the refusal names that command and the words that pass it; an item that may be empty is declared in the factory's null-outcome table and walked by a test. (tool: none yet)
- The class of a refusal says whose fault it is: a malformed request (the call's fault) and a story that is not ready (the story's fault) are different answers on different routes; a block about recorded state raises the state class, a block about the request raises the request class.
- A ban is never bypassed and never a dead end: it holds regardless of state (no exemption because a file already exists or a step already ran) and is never passed by a workaround (a heredoc, a helper script, another tool); every ban names its door -- the command that does the legitimate version of the refused act, and the person's word, which the ban accepts and records (P13); where the role can judge, the door is the role's, not a question: an interrupted artifact is continued by default (keep the rows that parse, validate and were built on the same inputs, repair the stale ones, set the rest aside as `.superseded` only when nothing is usable); a role that cannot judge and has no door files a finding and asks, and neither stops silently nor works around; a person's "delete it and start again" still reaches a command that executes it.
- Whatever the work needs from outside is tried by every route before a person is asked, and data is read by every route: the ticket, links, comments, attachments and repositories are read in a light form by the tracker's API, SSH or git for a repository, a browser where an API is closed; an LLM agent is never a read route (P5) -- it only writes, and only where the project writes that way, and a stored snapshot's provenance says fetched or pasted by a person, never an agent; what the factory's own probe proves unreachable is a reported gap, not a question; a person is asked only for access they can give, with three answers: not needed, here is how to get it, here it is as text; the refusal lists each route tried and why it failed; text a person pastes is a legitimate input for the story but never proves a fix to the route; a new ticket field or source read by the API route is compared with an LLM run, and anything less than the LLM output stops the change.
- When the factory cannot cope, does not understand or cannot act -- or code meets a state it has no move for -- it calls the conductor through one seam, and only that seam calls the conductor (P22); this is a principle of the whole factory, not the answer to one gate; the conductor is a helper for problems, called for a problem and never to run a command (P3): routine commands are run by code, triggered by a stage transition or by a question appearing, nothing the conductor does could be a fixed command, and every conductor call site names the problem that triggered it; the conductor gets the problem, the evidence and the doors as priced options -- everything that lets the work continue, each with its price and its consequences for the person and for the story -- executes the chosen one with existing commands and records a finding; it redoes nothing itself: it steers the factory -- calls an agent (through the controller), returns the factory to the needed stage, asks the person to do something; it settles the problem itself before it asks a person, always and everywhere: it reads what the code left (records, logs, notes, the refusal's evidence) and resolves what it can, and what the code recorded (a cause, a verdict, a refusal) is evidence for the investigation, never the text of the question; a person is asked only what only a person can know or decide -- a class of the factory's person-owned table -- and the question carries that class and what was read; the seam refuses a question without them once, then falls to its priced fallback with a factory defect; on the interactive road a person's word without a class is recorded and counted, not refused; code puts only closed questions to a person and reads only those, and any free answer is read by the conductor, never by code; a new conductor action is a data row, a phase line that tells the orchestrator to ask a person about a recorded state names its person-owned class, and a new stop goes through the seam or carries an inline reason (the out-of-seam rule, Contracts between code and roles); the run must not suffer: the worst allowed is the conductor spending unplanned money, never the factory standing still or promising and not doing. ## Text shown to a person
- Every text a person reads -- gate questions, boundary questions, a role's halt, a refusal the conductor relays, the report's factory-defects section, the closing question -- goes through the factory's one question form (P9): what the factory decided by itself, why the answer cannot be derived, exactly what is needed (one question), a closed set of answers, how to answer (at the bottom, the only place for a script name), and the price and consequences of each option for the factory, the person and the story; it uses the story's words; no filler stands where a question belongs; code reads back only the offered tokens, and a free answer goes to the conductor (P22); a question asked again changes its text; code checks outgoing text for form-field names, plugin paths, dispatch ids and internal row ids in its body (a presence check). (tool: none yet)
- Everything a person decides at a gate has an executor, and the decision is kept whole: a gate is a decision before the last stage, not the last stage; list everything the decision can order and point at the step that performs each item.
- One packet shown to a person does not contradict itself: sections that could disagree are computed from one source and read the same field.

## Contracts between code and roles
- If a contract requires a field from a role, a command in that role's own permitted set must emit it; otherwise the field is not required.
- A detector never reads a person's or a role's wording by a phrase list: code triggers on a field, a state or the presence of words; what words mean is judged by the role that owns the subject, or by the conductor.
- A path a role needs is given to it -- in its known paths or in the dispatch's own lines -- never searched for.
- A script's output shape is as much a contract as its arguments: if a caller parses stdout, nothing else goes to stdout; checked by running the script and parsing its output the way its caller does.
- What the rules say a party may do, the guard permits: for each permission stated in a reference, a test exercises the guard on that exact path.
- For every state the other side can return, this side has a move or a refusal that names who acts: enumerate the other side's states from its own source and match each to a branch; a state the code has no move for goes through the one seam to the conductor (P22), and a site outside the seam is found by an audit -- a site is outside the seam when it builds a stop or a person question itself, calls a function that returns one, or runs a factory script and drops or only prints its result; a site that stays carries an inline reason (`# remains: <reason>`), and the existing sites are a shrink-only baseline. (tool: none yet)

## Identity and evidence
- Evidence of execution is not evidence of coverage: a green run says what was built, not what was promised; "covered" is never written where "ran and passed" is meant, and a field's name says which of the two it carries.
- An identifier is resolved through the tool that produces it, at the moment it is stored -- not when it is read, and never from the author's spelling: the id is written after a call to the tool that enumerates it.
- Every state the factory can record has a sanctioned way out: a change that introduces a state names the command that reverses it and gives it a row in the state-exits table; stage run marks survive a second close; every state the other side can return has a move (Contracts between code and roles).

## Delivery and reporting
- Every blocking reason names its owner, and an unrecognised reason is a defect of the classifier: the default owner may not be `product`; a new reason family joins the owner vocabulary, not a list of exceptions, in the same change.
- The reason a delivery is not ready is stated in the task's own terms, first: the first blocking reason names a requirement, a behaviour or a user, not a receipt; the factory's bookkeeping goes in its own section below, marked as the factory's.
- A skip because the product lacks what a requirement demands blocks delivery; a skip by the factory's own decision does not; the two never share one word, and the blocking set holds the first; the verdict has three words and one reader; the third verdict `after_checks` (ready once the person finishes the checks left with them, P21) is never reached while a failure or a product gap stands, a verdict kind the delivery-verdict table does not hold reads `no`, and "Left with you" lists every handed-over item and the regression scope; every finding, bug or gap reaches the report under its own owner.
- A discrepancy with a requirement has a road to a bug file under the story's `bugs/` even when no test can fail.
- Every step has a recordable completed state for the null outcome ("nothing goes out", "nothing to file", "no failures to triage" are results): the empty state is recorded, not escalated, and declared in the null-outcome table. (tool: none yet)
- A report never changes the meaning of a role's own verdict: each distinct source verdict maps to its own reported state (rejected, unverified and approved stay three words).
- A capability the run's standing decision forbids is neither probed nor advertised: the probe reads the standing decision first, and the packet says the channel is closed by the person's word instead of confirming it.
- Nothing the factory writes or names is tied to one machine or one layout: every path named in text a person or a role reads is the path the code writes, and a stored or printed path is relative to the project root, resolved through the factory's one path resolver, never written by hand; a stored path is a hint, never a fact; a project may sit in a subfolder of a git repository, and one project-marker walk finds it. (tool: none yet)
- A comparison run leaves no trace in the project (P8): no merge request, no tracker comment or subtask; bugs go to a Markdown file or the chat; the run works on a copy; the experiment's external writes are closed and its record of outward writes is empty.

## Measurement and money
- A story's spend is the sessions its own journal names -- a record of what the factory launched -- not every session that mentions the ticket; a roll-up that cannot name its sessions says so instead of publishing a number (P18).
- When two records of the same quantity disagree, the report names the authoritative one, prints the gap and states the method behind each figure.
- A measurement is not a finding until the raw evidence is read: a count of refusals is not a count of defects, and the claim quotes an example from the raw record.
- A cache belongs to the run it measured and is keyed by that run; a report says out loud when it used one and names it.
- A measurer is code and gets a test like any other code: a measurement change ships with a case that fails without it.
- An unknown is never reported as a fact: a measure with no evidence says `unknown`, the reporting path has a distinct state for "no evidence", and the report prints that word.
- Work moved to a deterministic tool is judged by the LLM spend it removes; the tool's own cost is reported, not optimised; the change reports the LLM spend of the affected stage before and after (P6).
- Friction with the factory's own code is measured on every run, and code that makes a role's stage dearer than without it is a defect (P11): a turn is friction when our code returns a traceback, a hook refusal, an argument-shape error or a validator refusal of our own artifact, or when the role writes itself a helper script; the turn carries its full context cost; a change reports the affected role's code friction on a live run, before and after.

## Writing factory code
- Code bearing escape sequences is never written through a heredoc -- use an editor tool, or build the escape from `chr(92)` -- and no factory file carries a control byte 0x07, 0x08, 0x0b or 0x0c; a regex is proved to match in a test. (tool: none yet)
- Every fix goes to the root cause, with a case that fails without it and a green selftest, and the change names the cause; never a bigger model, a retry or a wider timeout; extra critic iterations are a missing self-check.
- A red test against a requirement is a bug, not a blocker: a discrepancy is the goal of the work; never re-read the requirement until the test agrees with the product, and no change by itself turns a requirement discrepancy into a blocked or waived row.
- A process someone reads while it runs writes line-buffered: it is started with `-u` or flushes at every progress line.
- A validator writes nothing -- not into the request, and not onto a copy the projection rebuilds; what it must record goes to a durable record of its own; replaying the same request with the same idempotency key after the validator ran still succeeds and reads that record back.
- The factory's roles run on Sonnet or Terra, never on Haiku (P7); a fix that holds only on a stronger model is not a fix: role files bind no other model, and a quality regression is fixed in the role's instructions or the code, never in its model line.
- Factory code needs nothing beyond the F10 runtime (Python 3 and pure-Python PyYAML): no new dependency.
- Text a factory run reads at every stage (a craft page, a stage's text) has no cap but is added tersely: every run pays for it.
- Where a factory document lives is decided by who loads it: a document injected into a role is capped per file because it is that role's context, a document nothing loads is uncapped and outside what binds a dispatch; a size cap is never the reason a document is split. (tool: none yet)
- A factory role gets only the tools its phase steps name and the context its work needs: its whole start load (charter, the project's CLAUDE.md, injection, packet, launch card, brief with its side files, form) is one number per role, summed in tokens, under one threshold, and text added to a role's start load removes at least as much. (tool: none yet: `stage_start_load` in forge/budgets.json is not set)
- A new factory CLI script is registered in the factory's list of scripts that an audit walks; an unregistered script is dead code shipped as if it ran; until that list exists, the script stands on its commit's `mechanism:` line. (tool: none yet)

## Universality across projects
- Open variety is a role's judgment; code reports and leaves a move, and never decides meaning (the detector rule, Contracts between code and roles): on a project shape the factory does not know (a value of a variety axis that no table row, key or role step names) code never blocks and never takes a default branch silently -- it says what it could not establish and leaves the move to the owning role, or to the conductor's seam when no role owns the state (P22), and the gate never passes on such a shape; a refusal naming a door the receiving role can take is not a block; the role proceeds as a free agent on the same model would, with what the factory already has (onboarding answers, testing knowledge, the critic), asks the person only for what it cannot find, and carries the stage to a result; work that code hands to a person goes to the role first, the person gets only what the role cannot do (a physical device, a credential), and a door that leads to a person past the role is not passage; a stage may cost more when that buys quality but never blocks; a default is silent unless it is declared in data and the run says it was taken; a safety refusal stays a refusal, and a person's word still passes any gate (P13); a change that moves a decision into code names what the role still decides, a change that reads the value of a variety axis says what it does on a value it does not know, and a changed script is run on one fixture shaped unlike the default and must report, not halt.
- Closed variety lives in data, never in code: a closed set of values (vocabularies, phrasings, tool and rate tables, tracker key forms, delivery commands, test-file markers, assertion shapes) lives in one data table with one reader, and a new project's value becomes a row, never a second regex at a site. (tool: none yet: forge/tools/universality.py scans names only)
- Every config key has a default: what varies per project is a config key or a strategy-file section, and onboarding asks for it; a fact only a person's answer can give lives in the answer registry, which has one writer and is read config first, registry second; a changed answer appends to its history, never overwrites; every template key has `since` and `absent_means`; migration fills missing keys and never touches a person's value, so a project onboarded on an older version runs without re-onboarding, and a story in flight is never refused because an earlier artifact lacks a new field; one commit carries the template row, the key row, the read with its default and the interview topic that asks it.

## One action, one way, everywhere
- A fact with a reader function is read only through it: every consumer calls the one reader, and a second parser of the same bytes is a defect even when it agrees today; before writing a reader, search for the same parsing shape with a positive control, and a new reader joins its axis row in the sibling map.
- A tool that exists for a problem is wired everywhere that problem occurs: a problem that recurs at many sites has one survivor, a hole is fixed in the survivor and every site calls it; a helper wired into three of four sites is not adopted; the sites are found by searching for the problem, not for the helper, and every site is listed; a site that cannot call the survivor is named on its axis.
- One artifact, one writer: every artifact a stage declares has exactly one writer, plus that writer's own machinery; code that needs another's artifact changed calls the owner's command or writes its own file; a new artifact gets its stage output and its writer in one commit. (tool: none yet)
- Detectors and refusals have one output shape and one reader: a detector prints one shape (a count line and one line per finding, capped by bytes with the full list in a file) and is read only through one reader; a refusal's lines are built once; a combined refusal lists every problem; a contract change updates the reader, every producer and the test in one commit. (tool: none yet)
- A change finds its twins: logic with a twin in another stage (a stage twin) is named with every side's files in the change's commit or report, and the change changes each other side or says why not; the twins on the sibling map (`forge/siblings.md`) are walked on any change, not only a defect fix.

## Continuity between stages
- Every field read has a producer; every field produced has a reader: whatever a script, role or phase reads (a field, config key, strategy paragraph, interview answer) has a producer the factory can run (an interview question, a permitted tool, a deriver); what is produced is read downstream or declared terminal; removing, renaming or rewording a producer removes or re-homes its readers in the same commit, found by a case-insensitive search of its name with a positive control.
- Every required list or field declares its empty outcome: exactly one home for "empty" -- a contract null outcome, a never-empty row with its guard, or a pending row that only shrinks; a null result is a recorded completed state, not an escalation; a new required field or list is declared in the commit that adds it, never born pending.
- Requirements, not code and not AC, are the unit from S2 to delivery (P23): completeness is counted by the S2 register's requirements through the plan, the cases, the binding and the verdict; an expectation comes from a requirement, never from the implementation (P20), and an unconfirmed one stays `unresolved: expectation_unconfirmed` and is reported as a gap; text that counts completeness says "requirement", and a new expectation names its oracle.
- A gate does not decide on an unknown, and an unknown never becomes a pass at a stage boundary: a gate that cannot read its input (missing, unreadable, no evidence, an unknown word) names what it could not establish and asks whoever can know with closed answers (the person for the world and for intent, a role for its own artifact), or, where nobody can answer, takes its declared safe default (run again, report a gap, refuse with a door) -- never a pass; it records the facts it read and where and how, and what it could not read and what it tried, and decides by a policy kept in data (the project's registry, grown by the answers of the person and the roles); a person's word is a verdict of its own (`person_confirmed`), bound to the facts it was given for, never shown as `matched`, void once they move; a new gate read states its behaviour on missing, unreadable and empty input, and a test pins it. (tool: none yet)
